The problem

Which model is best best at your code?

Every benchmark answers a question you didn't ask. They rank models on someone else's problems — not your weird build system, your house style, your flaky test, your half-finished refactor.

So we guess. We pick a favorite CLI and hope. We A/B by gut feeling across a dozen terminal tabs, lose track of which one is working and which one is stuck, and quietly trust whichever agent we happened to babysit that day.

Kaiju turns the guess into an experiment. One prompt, several CLIs, the same isolated starting point — and a verdict your own test suite signs off on. It's a control plane for a fleet of terminal agents, but the point is the bake-off: compare → judge → promote.

The bake-off loop

Compare. Judge.
Promote. Repeat.

  • 1

    Compare across CLIs

    One prompt fans out to N isolated runs — one per CLI, each on its own kaiju/<id> worktree branch. No shared state; they can't clobber each other. Watch the live diffs side by side.

  • 2

    Judge, objectively

    A local claude -p ranks the runs anonymized (A/B/C — it can't favor a brand). Hand it a test command and it runs your suite in each worktree, weighing pass/fail over looks. No API key.

  • 3

    Promote the winner

    One click commits a run's changes and merges its branch into your workspace. Refuses a dirty tree, aborts cleanly on conflict — and tells you the branch to merge by hand.

  • 4

    Keep score

    Every judged bake-off is recorded per repo. Open the Leaderboard to see which model wins most — and whose tests pass most — for this codebase.

Adopt a live session

Bring an existing Claude Code conversation under Kaiju by id — it resumes inside a managed tmux session and shows up in the dashboard (and on paired devices).

📥Scale

A task queue + bounded pool

Submit a backlog; a worker pool keeps up to KAIJU_CONCURRENCY agents running and drains the queue, each task isolated in its own worktree by default.

🔔Awareness

It tells you when it's stuck

A background monitor flags waiting-for-input, stuck and error — once, via console bell, native desktop notification, or Slack. No babysitting.

Under the hood

A layered Rust workspace.

One daemon binary. No external services. Works offline. The dependency rule is strict — the domain knows nothing about tmux, Axum, or git; adapters implement a single trait, so adding a CLI is one file.

kaiju-core

Domain types — Agent, AgentStatus, AgentMetrics — and the Adapter trait. No IO.

kaiju-adapters

Per-CLI adapters that build commands and parse output. One trait, one file per CLI.

kaiju-daemon

HTTP API, dashboard, store, tmux integration, task scheduler, and the background monitor.

kaiju-cli

The kaiju command-line client — spawn, list, logs, diff, send, attach, submit.

How a run works

From prompt to verdict.

A client asks the daemon to create an agent

From the CLI, the dashboard, or any HTTP caller — same API. Isolated runs get a fresh git worktree on a kaiju/<id> branch.

The agent launches as a tmux session's main process

The matching adapter builds the command. Because the agent is the session's process, the session ending is a clean "completed" signal — no exit-code guessing.

The monitor polls every two seconds

It captures the pane, parses it through the adapter, and updates status + metrics. Content-hash fingerprinting catches stuck; a confirmation gate keeps waiting-for-input honest. It alerts you once.

You read, reply, judge, promote

Check status / logs / diff, type into the live terminal, or attach to tmux directly. Then let the judge rank the runs and promote the winner into your branch.

Engineering notes

The logic is pure.
The world is a parameter.

Two recent reliability fixes share the same shape: push every decision into a pure function you can unit-test, and leave only the unavoidable IO in a thin shell. That's how an orchestrator earns trust.

A status detector you don't believe is worse than none

Agents stream output in bursts; a prompt-looking line scrolls past mid-thought. The old code trusted it instantly and cried "needs input." Now a fresh waiting signal is held until the pane has actually gone quiet — reusing the idle clock the stuck-detector already computes.

match base {
  // hold a fresh prompt until output is quiet
  WaitingForInput
    if current != WaitingForInput
    && idle_secs < wait_confirm => Running,
  Running if idle_secs >= threshold => Stuck,
  Stuck   if idle_secs <  threshold => Running,
  other => other,
}

Two agents, one port 3000

Isolated agents love to run npm run dev — and collide. Each isolated agent now reserves a free port (TCP-bind probed, base 41000) injected as PORT. The selection is pure, with the probe injected, so it's tested without opening a socket.

fn allocate(base, taken, is_free) -> Option<u16> {
  (0..MAX_ATTEMPTS)
    .filter_map(|o| base.checked_add(o))
    .find(|p|
      !taken.contains(p) && is_free(*p))
}
